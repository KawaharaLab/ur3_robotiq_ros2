# 収集後の物体単位の厳格チェック

`ac` の進捗JSONから、最終的に完了した全試行と、それらを記録した全bagを読み直す。収集後に実行する。既存の `acquisition_quality.json` の判定を再利用せず、元bagから検査する。

```bash
cd /home/tsumura/my_robotiq_ws
/usr/bin/python3 src/ur3_robotiq_ros2/utils/diagnostics/check_object_acquisition.py \
  --progress /mnt/nvme1/tsumura/masters_thesis/data/object7/automatic_jobs \
  --out ./object7_quality_check_20261111
```

`--progress` にディレクトリを指定すると、その直下で最終更新時刻が最新のJSONを選び、冒頭にパスを表示する。未完了の最新版を自動で飛ばすことはない。過去の特定の収集を確認する場合は進捗JSONファイルのパスを直接指定する。`--out` は新しいディレクトリを指定する。再実行時は末尾に `_run2` などを付ける。

このコマンドはソースのPythonファイルを直接使う。コードの反映後、そのまま実行できる。ROSノードやロボットの起動は不要。Python環境に `cv2`、`numpy`、`yaml` が必要。従来の `.db3.zstd` には `zstd` コマンドも必要。JPEGは一枚ずつメモリ上でデコードし、画像ファイルを展開しない。全画像デコードとbagの複数回走査があるため、検査には時間がかかる。収集中のPC負荷を避けるため収集終了後に実行する。

## 判定と対応

| 判定 | 終了コード | 対応 |
|---|---|---|
| `PASS` | 0 | 検査範囲で問題なし |
| `PASS_WITH_NOTES` | 0 | 問題の内容と補完条件を記録済み。追加の個別調査は原則不要 |
| `REVIEW` | 1 | 該当セッション・試行を調査する |
| `FAIL` | 2 | 破損・未完了・検査失敗など。原因を解消して再検査する |

`PASS_WITH_NOTES` でも、ローカル時刻情報の結合や生パケットからの力覚復元が必要な場合がある。既存の通常エクスポートはこの補完を自動では行わない。元bag、進捗JSON、セッション内の `gelsight_acquisition_records` を一緒に残す。補完可能性は検査で確認するが、このコマンドによる学習用データの書き換えはない。

まず `summary.txt` を読む。`REVIEW` / `FAIL` のときは出力フォルダ全体を共有する。`summary.json` の `needs_investigation` に対象セッションと理由がある。セッション別フォルダには画像・DB検査、通常QA、ローカルとの照合、時刻スキーマ・生パケット値検証、試行別指標がある。`summary.json` は途中経過も保存するため、`RUNNING` の状態では合格扱いにしない。

## 検査内容

- 進捗JSONの凍結済み計画・条件・識別子の整合性、全試行の完了、最終完了attemptの一意性。
- SQLiteの `quick_check`、全トピックの実メッセージ数とmetadataの一致、分割bagの全ファイルの読み出し。破損した圧縮bagの復元は別途調査する。
- 完了attempt内に一意なSTART/ENDがあること、押し込み・揉みの計画に対応した成功アクション数、イベントの対応関係。
- 全GelSight JPEGの構造とデコード、画像サイズの変化。
- 左右GelSightの追加時刻情報を、bagとローカルの両経路で照合。ローカル書き込みの欠落・終了状態・不正行・ストリームの不一致も検査。
- 時刻記録のスキーマ、ステージの順序、時計ブラケット、シーケンス、各attemptに記録されたセンサのストリームIDとの一致。
- 力覚の6軸の有限性、追加時刻情報内の生パケットから復号した6軸とWrenchの一致。試行内のWrenchが全件生パケットで確認できなければ要調査。
- 試行内の欠落、境界の被覆、レート、時刻の重複・逆行、配送遅延、カウンタ増加。
- 無荷重基準が残っていること、基準からのFy最大変化、単発スパイクの疑い。
- provenanceとinit参照の欠落・不一致、検査中のソースファイルの変化。

## 厳格チェックの既定値

これらはデータの詳しい調査を促すための判定値。動作中の中断条件を変更するものではない。

| 項目 | `REVIEW` とする条件 |
|---|---|
| GelSightの試行内間隔 | 100 ms超 |
| 力覚の試行内間隔 | 生パケットによる補完分を含めても5 ms超 |
| 試行境界からセンサ記録まで | GelSightは100 ms超、力覚は10 ms超 |
| Headerによる試行内平均レート | GelSightは17.5〜20 Hzの範囲外、力覚は950〜1050 Hzの範囲外 |
| 試行内の生成元シーケンス欠落 | 1件以上 |
| 画像Headerからbag記録まで | p95が50 ms超、最大250 ms超、または−10 ms未満 |
| 力覚Headerからbag記録まで | p95が200 ms超、最大500 ms超、または−10 ms未満 |
| 単発スパイクの疑い | 両隣のFyの差が0.5 N未満で、中心が両隣それぞれから2.5 N超離れる |
| 完了試行内の力上限超過 | 無荷重基準からの絶対Fyが計画のhard_limit_n以上となるサンプルがある |

通常QAで見つかる時刻追加記録の欠落・配送遅延がローカル保存で補える場合や、Wrenchの欠落を生パケットで補える場合は、厳格チェックの被覆検査等を通ったうえでNOTEにできる。厳格チェックで補えない欠落・スキーマ異常があればREVIEWになる。

厳格な欠落判定は採用する完了試行のSTART〜ENDに適用する。記録開始直後・終了直前や中断attemptの情報は別途通常QAに残す。JPEG検査とDB整合性検査はbag全体に適用する。カウンタはセンサ起動からの累積値なので、増加前の既存値だけでは試行中の故障と断定しない。

`--skip-image-decode` はトラブル時の診断用。デコードを省いた結果は必ずREVIEWとなる。

検査は物理的な露光時刻・ADC時刻の校正、画像内での接触の妥当性、実際の押し込み量・機械的形状を保証しない。スパイク候補や配送遅延の指摘も、そのまま全試行の取り直しを意味しない。該当試行を確認して判断する。
